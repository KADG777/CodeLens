# 评估材料及结果边界

这份说明于 2026-10-02 随测试交付补齐，不包含用户业务代码或用户审查报告。仓库提供合成用例、原始模型结果和开发标注，供核对方法、失败案例及指标。以下历史结果属于 2026-09-28 开发阶段，不是对本轮工具发现补回、容量处理改动的真实模型复测。

## 历史 v4 主审：三种策略

原始结果为 `quality-direct.json`、`quality-tools.json` 和 `quality-full.json`；逐条标注为 `quality-annotations.json`，其 `sha256` 绑定对应原始文件；复算汇总为 `quality-summary.json`。三组各使用同一组 10 个短合成输入，模型为当时配置的 `deepseek-flash`。

| 策略 | 预设缺陷命中 / 5 | 正式 / 待确认条数 | 所有意见中的错误 / 缺少上下文 / 可选建议 | 平均秒 |
|---|---:|---:|---:|---:|
| direct | 5 | 0 / 15 | 2 / 3 / 5 | 1.986 |
| tools | 5 | 1 / 21 | 4 / 3 / 10 | 3.801 |
| full | 5 | 7 / 11 | 2 / 6 / 5 | 4.451 |

完整模式的 7 条正式意见里，5 条匹配已知缺陷，2 条依赖未知业务意图；待确认中仍有 2 条错误。因此，“5 个预设缺陷均命中”不能表述为准确率 100%。这份标注是开发复查，不是独立人工盲评；样例还用于设计提示词和规则，不能作为未见输入的泛化测试。

## 历史追问与 v5 定向实测

`quality-followup.json` 保留最终五场景六轮追问和逐场景开发复查；`followup-iteration-1.json` 至 `followup-iteration-5.json` 保留改动过程中的失败和修正，不能只看最后一次成功。明确的本地事实可能零 API 调用，不能把这种回答算成模型识别正确。

`evidence-v5-iteration-1.json`、`evidence-v5-iteration-2.json` 和 `evidence-v5-preprocessing-final.json` 记录三份合成代码的两轮审查及一次预处理定向重测。第二轮结果以 `evidence-v5-iteration-2.json` 为准，内容完全相同的汇总副本已移除。它们验证了多位置证据和工具归属的处理，也暴露出模型会猜测预处理极性或接口意图；部分候选最终只是被拦截，并未被模型稳定修正。文件中的 `human_review.reviewed=false` 不能被误读为独立评审已通过。

## 历史速度观测

`performance-v3.json` 保存固定合成源码在历史两实现上的各两次结果。均值为 16.65 秒 → 6.03 秒，模型调用 4 → 3，输出 token 3477 → 1020，输入 token 基本持平。样本只有一个、每版两次；服务负载和生成随机性都会影响耗时。这些数字不是当前提交的性能保证，也不能与其他输入的单次耗时直接比较。历史引擎未随仓库交付，因此可以核对原始记录，但要复跑对照必须另行提供相同基线。

## 本轮提交修正应怎样验收

本轮重点是最终报告不遗漏已经运行的静态检查，以及容量限制不静默丢弃末尾高优先级问题。对应场景由 `tests/test_tool_reconciliation.py` 和 `tests/test_truncation.py` 稳定复现，不依赖真实模型是否恰好遗漏某条发现。

从原开发目录补齐的 10 个测试文件、评估脚本、配置和历史合成结果现在随仓库交付，解决了“文档称有测试，但克隆后 pytest 没有收集”的材料缺口。当前回归数量、结果和新增真实模型记录应以本轮验证记录为准；本说明不把历史 203 项通过或历史端到端结果当作当前版本已经验证的证据。

## 2026-10-02 本轮真实 API 演示

第一轮原始记录：[submission-20261002-iteration-1.json](../evals/results/submission-20261002-iteration-1.json)。使用当时配置的 `deepseek-flash`、Python 3.12.9，对 `record_demo.py` 内置两份合成代码运行 full 工作流。记录包含该轮运行时源码 SHA-256，区别于以上历史实现；工具调用、实际反馈、初审 JSON、复核 JSON 和报告可逐项核对。下表是第一轮观测，不是后续修正的最终验收。

| 输入 | 预设缺陷 | 实际工具 / 模型调用 | 秒 | 本轮检查 |
|---|---|---:|---:|---|
| Python | 可变默认参数、字面量除零 | 2 / 3 | 3.85 | 真实静态工具已调用，复核完成，两项规则结果均保留 |
| C++ | `new[]` 与 `delete` 配对错误 | 2 / 3 | 3.09 | 真实静态工具已调用，复核完成，L3 规则结果保留 |

两例各有 3 次 HTTP 尝试，无请求重试。这是两例端到端流程演示，不是新增通用质量分数。模型未在此演示中恰好产生所有漏写或容量场景，因此这些边界仍由确定性的模拟回归验证。

第一轮输出包含跨行重复：Python 的同一除零问题分别锚到函数声明行与除法行，C++ 的同一释放问题分别锚到分配行与释放行。两例的条目数为 3 和 2，不能当作 3 和 2 个独立缺陷。这一轮保留用于解释后续修正，不能只展示较好的最后结果。基于原规则编号和唯一原样引用恢复实际工具位置后的重测应另行记录；保留真实工具发现不等于已解决所有自然语言重复或语义质量问题。

最终修正后的重测：[submission-20261002.json](../evals/results/submission-20261002.json)。运行时源码 SHA-256 与本轮最终实现一致。Python 保留 2 条真实规则（AST005 L6、AST002 L1），C++ 保留 1 条真实规则（CPP006 L3），没有待确认项；首轮观察到的跨行重复在这两例中消除。两例各 3 次模型调用、2 次工具调用、3 次 HTTP 尝试，无重试，分别耗时 3.66 秒和 4.51 秒。真实静态工具调用、复核完成、预设规则/位置保留三项验收均通过。

本轮完整自动化回归 **239 项通过**，Ruff 检查通过。新增回归覆盖模型漏写、已否决不复活、31 条与 40 条以上容量限制、同行多个诊断及跨行唯一规则定位。真实模型的两例结果和这些确定性测试证明相应流程可复现，不证明通用准确率，也不保证其他自然语言意见没有误报或重复。
